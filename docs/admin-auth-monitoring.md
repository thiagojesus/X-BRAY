# Admin authentication and operational monitoring

Status: Phase 2 backend implementation in code; auth remains disabled unless explicitly configured. This is not production readiness or a completed independent security review. Google provider setup, redirect allow-list setup, initial membership grant, production migration application and deploy are owner-controlled and have not been performed.

## Accepted boundary

MVP: Google sign-in through Supabase Auth; Apple is future-only. Admin membership is an explicit server-side grant, never inferred from domain/email/Google identity/frontend state/editable metadata. No public signup role assignment or admin-management UI. Admin portal is read-only operational visibility. Existing public APIs retain current contracts; human sessions never authorize refresh/resume/probe/write operations, and existing automation auth remains unchanged.

## Authentication design (phase 2)

Use official maintained minimal package `supabase-auth==2.33.0`, not deprecated `gotrue` nor whole `supabase` client. Project runtime tested: Python 3.14.7; package resolver successfully installed it alongside pinned FastAPI 0.115.0 and HTTPX 0.27.0 without upgrading either. Package constraints: HTTPX `>=0.26,<0.29`, Pydantic `>=1.10,<3`. Exact calls: `SyncGoTrueClient(url=..., headers=..., storage=..., flow_type="pkce", auto_refresh_token=False)`; `sign_in_with_oauth({"provider":"google","options":{"redirect_to": callback,"scopes":"openid email profile"}})`; `exchange_code_for_session({"auth_code":code,"code_verifier":verifier,"redirect_to":callback})`; `get_user(access_token)`. Inspected SDK source confirms PKCE begin stores generated verifier through injected storage under `<storage_key>-code-verifier`, exchange explicitly accepts verifier and posts `grant_type=pkce`, and `get_user(jwt)` makes Auth `/user` request. Each request gets an isolated client; never use implicit process-local verifier/session state. Offline two-client mock proof: `/private/var/folders/l2/c_yyrb2d4slcjvqn_s3j224w0000gn/T/opencode/xbray-auth-spike/spike.py`; run `cd /private/var/folders/l2/c_yyrb2d4slcjvqn_s3j224w0000gn/T/opencode/xbray-auth-spike && .venv/bin/python spike.py`. Result: PASS; begin verifier restored by independent callback client, explicit exchange and verified mocked `/user`, two mocked HTTP calls. No real provider connection/user/credential. Source inspected in installed `supabase_auth/_sync/gotrue_client.py`; package version resolved as 2.33.0.

Use FastAPI BFF and configured canonical URLs only. `GET /api/auth/login` begins Google PKCE; `GET /api/auth/callback` processes exchange; `GET /api/auth/session` returns minimal no-store identity/authorization DTO; `POST /api/auth/logout` revokes/clears; `POST /api/auth/activity` qualifies idle renewal. Google provider OAuth redirect registered at Supabase: `https://ajczxqrrqmvjzuthxjca.supabase.co/auth/v1/callback`. Application callback bases are production `https://xbray.vercel.app/api/auth/callback` and development `http://localhost:5173/api/auth/callback` only in explicit dev mode; the Supabase destination allow-list adds only the narrow escaped-query pattern described below. No preview wildcard. Never construct redirects from incoming `Host`, `X-Forwarded-Host`, or `Forwarded`; callback checks `Host` only as a transport allowlist, while callback and user redirects always use configured canonical URLs. Existing Vercel `/api/*` proxy maintains same-origin browser cookie behavior.

### External rewrite transport contract

The repository rewrite is `/api/:path*` to `https://xbray-api.vercel.app/api/:path*`. Vercel's current [external rewrites documentation](https://vercel.com/docs/routing/rewrites), fetched 2026-10-31, describes external rewrites as forwarding requests and says Vercel forwards `x-forwarded-host` identifying the original visitor host. It does not specify whether the origin's `Host` is the original frontend authority or destination backend authority, nor guarantee a stable Host contract for this deployment. Treat that detail as undocumented/unverified. The server explicitly allows only the two configured exact production ingress authorities (`xbray.vercel.app`, `xbray-api.vercel.app`) for the callback route, so either transport shape is supported without trusting forwarded headers. This does not verify the hosted rewrite; an owner-controlled hosted OAuth roundtrip remains a publication gate.

Session cookie: random 256-bit opaque credential, `__Host-xbray_admin; HttpOnly; Secure; SameSite=Lax; Path=/;` no Domain; separately named non-Secure cookie only for explicit localhost development. Store only hash in DB. Rotate at successful login; atomically install new session and revoke prior session. Enforce 30-minute idle / 8-hour absolute limit; absolute never extends. CSRF is deterministic HMAC-SHA256 with distinct `xbray:csrf:` domain over raw session cookie and server `ADMIN_SESSION_HASH_KEY`, so GET/session and reloads derive the same stable token across tabs. Persist only SHA256 of derived CSRF; never persist raw session/CSRF. Token is returned only in minimal DTO and is not authorization. Logout/activity require CSRF header, constant-time comparison, and exact configured `Origin`; no wildcard credential CORS. Login flow has separate browser-bound state. Auth responses `Cache-Control: no-store`.

### Durable OAuth flow and replay control

Supabase controls upstream OAuth `state`; the browser is returned to the app with a PKCE `code`. Application correlation uses separate `flow_state`. Source contract checked at official Supabase Auth commit `a7e97d665b9ea03853edb66d014bcde323f7894b`: [`GetReferrer` and `IsRedirectURLValid`](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/utilities/request.go) select/validate full `redirect_to` and glob-match the full URL minus fragment (`?` is a single-character wildcard and must be escaped as `\?`; `*` cannot cross `.` or `/`); [`GetExternalProviderRedirectURL`](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/external.go) stores the referrer in flow state and the PKCE callback appends code to that referrer. Source has a test preserving redirect query parameters on error; this is source evidence, not proof of hosted project version/config. Add ONLY narrow allow-list glob `https://xbray.vercel.app/api/auth/callback\?flow_state=*` and corresponding exact localhost path; never wildcard host/path. BFF accepts only its fixed callback route and exactly one canonicalized `Host` from the explicit ingress allowlist, exactly one 43-character base64url `flow_state`, exactly one bounded code, matching flow row/cookie binding/PKCE. Host authorizes no identity or admin access. `ADMIN_ALLOWED_REDIRECTS` must contain exact `callback\?flow_state=*`. Production auth stays disabled until owner setup and hosted smoke.

For each login generate random flow handle, browser-binding secret, and `flow_state`, each at least 256 random bits. Persist hashes of handle/state/binding; encrypt PKCE verifier using maintained `cryptography` AES-GCM with unique random 96-bit nonce and server-only versioned key. Set HttpOnly Secure SameSite=Lax `__Host-xbray_oauth_flow` cookie containing opaque handle+binding. Flow row binds exact callback URL, created/expiry (10 minutes), consumed, AEAD nonce/key version/ciphertext. SDK injected storage captures its verifier; callback loads/decrypts across instances and passes explicitly to exchange. Atomic conditional consume before exchange permits one concurrent winner; exchange failure consumes, restart rather than retrying ambiguous code. Missing/tampered/expired/replayed flow denied and cookie cleared. No cookie-only replay, custom crypto, shared client, or code/state/token logging. Responses use no-store, Referrer-Policy no-referrer, and fixed safe app paths/enums. App code never logs callback query, OAuth code/state/token/cookies. Edge/access logs are external and must be checked/configured by owner before production smoke; application code cannot control platform request logging.

### Tokens, idle activity, errors

After exchange, call SDK `get_user(access_token)` for authoritative stable Supabase user UUID, then discard Supabase access, refresh, and provider tokens. App session is independent; no upstream token persistence/refresh. Scope only `openid email profile`; no provider data API scope/offline access. Google/Supabase logout or disable does not magically revoke existing opaque app sessions; expiry/local revoke governs app access. Membership is checked on every private request.

`POST /api/auth/activity` takes no client timestamps; exact-origin + CSRF protected. Frontend later calls only on qualifying visible user interaction, no more than once per 60s. DB time updates activity/idle expiry only for unexpired/unrevoked session and caps idle expiry at absolute expiry. Session GET, admin GET, polling, hidden-tab traffic do not renew. Activity is advisory, not proof of human. Conditional update cannot revive expired/revoked session; logout/revoke wins races. 401 invalid/expired session clears cookie; 403 active session without membership revokes/clears with no authorization detail. CSRF/Origin 403 does NOT mutate session or clear valid cookie. Authorized logout revokes then clears; invalid session clears as appropriate; 503 does not claim revocation and does not clear a valid cookie. Auth requests are excluded from market/provider telemetry and ingestion ledger.

## Config, entities, provisioning

Names only: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `ADMIN_SESSION_HASH_KEY`, mandatory 32-byte `ADMIN_FLOW_ENCRYPTION_KEY`, `ADMIN_FLOW_KEY_VERSION`, `ADMIN_APP_ORIGIN`, `ADMIN_OAUTH_CALLBACK_URL`, `ADMIN_AUTH_INGRESS_HOSTS` (comma-separated exact host authorities, explicitly listing both canonical frontend and backend authorities in production; local HTTP dev must list only its configured loopback authority and port), `ADMIN_ALLOWED_REDIRECTS`, `ADMIN_SESSION_IDLE_SECONDS` (1800 default), `ADMIN_SESSION_ABSOLUTE_SECONDS` (28800 default), `ADMIN_AUTH_ENABLED` (default false), and `ADMIN_AUTH_DEV_HTTP_COOKIE` (only permits explicitly configured localhost HTTP development). Ingress hosts reject wildcard, path/query/userinfo, duplicate, malformed and suffix-matching forms. Never `VITE_*`. Google client secret exists only in Supabase provider configuration. No secrets/values in repo.

Migration `022_admin_auth` follows immutable `021_treasury_intent_trace`; it was added to the registry and exercised for SQLite and native PostgreSQL 17 (idempotency included). No FK assumption to managed `auth.users`; user UUID references are obtained from verified Auth identity. Tables: `admin_memberships(user_id UUID PK, granted_at, granted_by, revoked_at, reason)`; `admin_sessions(id, unique session_token_hash, user_id, created_at, last_activity_at, idle_expires_at, absolute_expires_at, revoked_at, csrf_token_hash)`; `admin_oauth_flows(id, unique flow_handle_hash, state_hash, browser_binding_hash, verifier_ciphertext, nonce, key_version, callback_url, created_at, expires_at, consumed_at)`; `admin_auth_events(id, user_id nullable, event, created_at, short reason)`. No email, plaintext OAuth material, IP, or unnecessary PII. Auth tables have RLS enabled, no anon/authenticated policies, plus explicit privilege revokes for those roles when present. Do not assume RLS protects the owner/backend role. Migration is additive and does not rewrite 021.

Bounded cleanup: indexed batched deletion of flow rows whose expiry is older than 24h, expired/revoked sessions older than 30d, and auth events older than 180d; run on an authorized backend maintenance host with `python -m scripts.admin_auth_membership cleanup --batch-size 200`, not on request paths. The CLI operates on the locally configured backend DB; production execution requires owner approval and correctly scoped backend runtime configuration. No external rate service; login flow starts are limited per browser binding, without retaining IP/PII. Grant/revoke and session revocation plus audit event are transactional. First login may create a Supabase Google user but denied user gets NO app session; responsible project operator privately verifies stable UUID, grants via controlled backend-only operation with actor/time/reason (CLI `grant USER_UUID --actor-id OPERATOR_UUID --reason operator-approved`), then user retries login. `revoke` disables membership and its sessions. Never email/metadata grant. These operations are not HTTP routes.

### Browser client contract (phase 3)

The browser calls only relative same-origin `/api/auth/session`, `/activity`, and `/logout` endpoints with `credentials: same-origin` and `cache: no-store`; CSRF is kept in React memory and sent only in `X-CSRF-Token`. The public application shell does not poll or call auth endpoints. `/api/auth/login` starts only by top-level same-origin navigation (not XHR); PKCE and callback handling stay server-side. If the session precheck succeeds but the login route subsequently fails its own auth/provider/database check, the current backend responds with a generic JSON error page (503, or a bounded 429), not a provider redirect. The client does not attempt CORS/XHR fallback; a user can return to the login page and retry. Callback errors redirect to fixed `/login` enum reasons. This UI behavior is not proof of hosted OAuth or external rewrite behavior.

The private route hides content during session checks, on expiry, on resume/focus, and immediately on logout or uncertain activity/logout results. Only visible pointer, keyboard, or touch interaction may request activity, throttled to one request per 60 seconds; polling and session GET never renew. Private session data and CSRF stay in memory, never browser storage. Session 401 and membership-denial 403 clear private client state; an activity/logout `403 request_forbidden` is distinct from membership denial and causes session revalidation rather than an assumed logout. Logout network/5xx errors hide the private view and report that server logout is unconfirmed, with only an explicit retry. Phase 3 presented an auth placeholder; the monitoring APIs and data described below are implemented in this branch. Hosted OAuth remains unverified.

## Private read-only monitoring API (phase 4)

All `/api/admin/*` endpoints independently use the active human membership dependency. Automation auth is not sufficient. Every status, validation and error response has `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; unavailable persistence returns only `503 {"detail":{"error":"admin_data_unavailable"}}`, without DSN, SQL or traceback. Routes are GET-only. No read calls refresh, acquire work, update business state, run source audit/probes, or lease a circuit. Reads never renew human idle sessions. The implemented UI polls only while visible.

Shared envelope fields: `generated_at` and `as_of` are UTC RFC3339 timestamps emitted by the API for this response; they indicate observation time, not transaction-time history. `scope` describes the bounded persisted/catalog subset. Unknown enum or legacy metadata is projected as `metadata_unknown`/`not_recorded`; unknown values do not become success. DTOs are curated projections, never database rows.

### Routes and DTOs

* `GET /api/admin/overview`: `latest_attempt` (greatest persisted `(created_at, run_id)`), `latest_fully_successful` (greatest run with recorded state `succeeded`), `active_runs.count` (persisted state `running`), latest-attempt `task_counts` grouped by persisted task/status, and `latest_valid_captures` by curated provider. Empty storage is `state: "no_backend_run_record"`, not a synthesized failure. Capture timestamps require a matching durable acquisition receipt (SGS additionally requires a plan-bound unit commit). The overview capture map is a separate current read model; it does not rewrite a run's historical task result.
* `GET /api/admin/runs`: defaults to 50, allows 1–100, uses `created_at >= since AND created_at < until`, and defaults to the last 30 days. Explicit bounds must be timezone-aware and ordered. Optional `state` is exactly `running|succeeded|partial|failed`. Results sort by timestamp then ID descending. Opaque URL-safe cursor binds limit/period/state and keyset position; changed filters are rejected with 422. Page includes `has_more`/`next_cursor`, counts grouped in a single bounded query for selected run IDs, and only numeric validated IDs receive the fixed GitHub Actions deep link. The first-page upper time is the pagination anchor; no claim is made about runs inserted later with backdated creation timestamps.
* `GET /api/admin/runs/{run_id}`: exact-run summary plus `task_page` (default 50, max 100; `task_cursor` is the last `task_order`). Unknown run returns 404 after authorization. The task page has full selected-run count and grouped `counts_by_status`; task projection includes the stored state, real `attempt` count, timestamps/duration where parseable, actual counts, bounded retry time, and allowlisted error category/code; claim token/expiry, raw details and arbitrary traces are excluded. Plan metadata is limited to its recorded version, as-of and validated digest; a missing plan is `not_recorded`, not regenerated from today's catalog. Final JSON is parsed only up to 64 KiB and reduces to an allowlisted status plus task count; malformed/unsupported payloads say `metadata_unknown` or `not_recorded`. Diagnostics use only that run ID and the existing sanitizer; absence/legacy versions remain explicit. Detail does not merge current proof/catalog state into its frozen result; `current_freshness` is explicitly `not_included`.
* `GET /api/admin/providers`: fixed provider registry `bcb_sgs|focus|tesouro|anbima|b3|ibge_sidra`. Circuit state and timestamps are a read of persisted `source_access_state`; an expired persisted open/half-open state stays recorded as such and is projected `next_admission_reassessment_due`, never silently closed. Receipt-backed latest captures and allowlisted latest error categories are separate facts. Missing state/diagnostics are `not_recorded`; no probe/admission helper is called.
* `GET /api/admin/coverage?provider=...&limit=50&cursor=0`: all six registered providers `bcb_sgs|focus|tesouro|anbima|b3|ibge_sidra` accept the bounded read contract; an unrecognized value remains 422. SGS uses its approved per-series catalog/freshness metadata and validated plan-bound receipts. Other registered providers do **not** borrow SGS series, calendars, or gap logic: today they return `coverage_status: "metadata_unknown"`, a specific missing-provider-contract reason, null `item_count` with `item_count_status: "metadata_unknown"`, and `items_status: "not_recorded"`. Their safe provider-level `latest_valid_capture_at` is preserved only from the same persisted receipt projection as `/providers`; for `tesouro`, a receipt-backed `treasury_cohort_commits.reference_max` is also returned with its capture time. Missing facts remain null/`not_recorded`, not fabricated. SGS page limit is 1–100, catalog provider-code ascending, with integer catalog-position cursor. Series identity/name/frequency/unit, configured start, BCB-documented start/first reference period where available, exact validated latest reference/capture, configured `freshness_days`, and at most ten exact archive intervals are returned. SGS status flags may coexist: `acquisition_unverified`, `history_pending` (only when the bounded candidate search was complete), `stale_reference`, `before_documented_start` (excluded, not a gap), and `metadata_unknown`. SGS 226 retains full-period identity and existing catalog period semantics. No speculative missing observation, future period, weekend, holiday, or monthly/annual gap is generated.

### Read/query bounds and provenance

Run history uses bound period/state parameters, stable `(created_at, run_id)` keyset ordering, `limit + 1`, and one grouped task-count query for the returned page (not one query per run). Migration 023 adds SQLite expression indexes matching that history/state ordering; PostgreSQL history retains timezone-aware casts and has no misleading raw-text chronology index. Detail fetches one run, one task page plus grouped status counts and plan metadata, and the exact-run diagnostics projection capped at its established 500 rows. Provider projections use a fixed six-source registry and bounded persisted-state/failure/receipt reads.

SGS coverage runs exactly two batched SQL statements per nonempty catalog page (capture candidates and archive receipt candidates), independent of series count; a page contains at most 100 codes. Each selected series uses an indexed ordered seek with `LIMIT 129`: 128 candidate rows plus one exhaustion sentinel. Thus at most 12,900 candidate rows per statement/page enter subsequent validation joins; SQL values are bound and SQL identifiers/fragments are fixed constants. `candidates AS MATERIALIZED` applies these per-series limits **before** the exact plan/commit/extraction validity joins. The capture seek orders `(captured_at DESC, operation_id DESC)` using `sgs_unit_commits_series_capture_idx`; the proof seek orders `(requested_start, requested_end, captured_at, operation_id)` using the migration-023 partial `sgs_coverage_receipts_admin_candidates_idx` (only BCB SGS archive/reconcile receipt rows). Window ranking/counting occurs only on these bounded candidates and validated matches, never on the full receipt/commit history. The proof query returns at most 11 validated rows per series: ten DTO intervals plus a valid-proof overflow signal. The response separately reports `proof_intervals_truncated` (more than ten validated matches in inspected candidates) and `proof_search.status/candidates_examined/budget_sentinel_present` (search incompleteness). When the 129th candidate is present, a missing proof or missing valid capture is `metadata_unknown`, not `history_pending`/`acquisition_unverified`; exact proof rows already validated remain identifiable, while completeness stays unknown. A valid capture in the newest bounded candidate set is still the latest valid capture because all newer candidates were considered in sort order. Index seeks bound output and validation work to the fixed candidate limit per series, but do not claim a universal constant bound on internal B-tree page visits or on checking candidates against the exact validity tables.

SQLite `EXPLAIN QUERY PLAN` tests with >129 candidate rows assert both coverage candidate indexes and materialized bounded candidates are used. Native PostgreSQL 17 integration seeds 1,500 unmatched commits and receipts for each of three catalog series, runs `ANALYZE`, executes the actual statements under `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, and asserts indexed candidate scans, one loop per per-series limit, and no more than 129 rows per limit. These are representative disposable-fixture plan/cost checks, not production query measurements. The new partial archive index is added in the still-unreleased migration 023; it does not rewrite migrations 001–022 or business data. All stored run/task/error/final JSON remains untrusted and allowlisted.

No `observation_missing` status is asserted by this version: there is no verified per-provider calendar for general missing-point inference. `availability != acquisition`; current catalog and proof inventory never change frozen run scope or the evidence then known. For Phase 5, preserve this distinction and ensure private fetch/cache state is scoped to authenticated identity/epoch; late responses from an earlier identity/logout must not republish private content.
